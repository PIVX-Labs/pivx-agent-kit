# Plan: v0.7.0, "a safe, auditable, dollar-priced agent wallet"

Date: 2026-10-01
Scope: growth levers #1 (spending limits plus human sign-off), #2 (spending history) and #4 (dollar amounts) from [`docs/growth-levers.md`](../growth-levers.md). Two bugs are fixed along the way because the new code touches them directly: the `task approve` double payment and the `--from` typo.

## Goal and pitch

> Give your agent a wallet with a spending limit, a receipt for every payment, and prices in dollars.

When this ships, an operator can run one command:

```bash
pivx-agent-kit policy set --max-tx '$25' --daily '$50' --approve-above '$10'
```

After that, they know the agent can never spend more than $50 a day, that anything over $10 waits for their approval, and that `pivx-agent-kit history` shows every payment with the agent's stated reason.

## Design principles

1. **One choke point.** All spending already flows through `core::send` (`src/core.rs:221`), whether it comes from a plain send, `task approve` or `cards order pay`. Limits, the ledger and USD conversion all live in or next to that function, so every path that spends is covered without separate wiring.
2. **Pure core, thin I/O.** Policy evaluation, ledger reduction and USD math are pure functions with table tests. File and network I/O sit in small wrappers around them, matching how the kit already wraps `pivx-wallet-kit`.
3. **Additive outputs.** Existing JSON fields keep their names and meanings. New fields are only added. With no policy file, the kit behaves exactly as v0.6.1 does.
4. **Fail closed on money.** If a limit can't be evaluated (corrupted policy file, USD limit with no price), the spend is blocked with a clear error. Display-only features (USD in `balance`) fail open and just leave the field out.

## As built (PR 1), deviations from this plan

PR 1 was implemented and then revised after an independent review. Where the shipped code differs from the sections below, the code and this list win:

- **Txid check done.** Double-SHA256 of the raw bytes was confirmed against real mainnet v1 and v3 Sapling transactions (`testdata/`), so the 1.4 fallback isn't needed.
- **`fee_sat` lives on `send_intent`**, not `send_broadcast`. The fee is known once the transaction is built.
- **`core::send(&SendRequest)`** takes a reference. `usd_price_e8` is passed to `payment::commit` rather than stored on `SendRequest`, and PR 2 fills it in.
- **New `src/payment.rs`.** The guard re-check, intent, broadcast and outcome steps moved out of `core::send` behind a `Network` trait so they can be tested with a fake network.
- **Spend lock.** `ledger.lock` (`std::fs::File::lock`, so Rust 1.89+) is held for the whole of `core::send`. The double-pay guard re-runs under it.
- **In-flight window is 600 s, not 120 s.** A compile-time assert keeps it above the worst-case send time, and a `failed` record that young also counts as in flight.
- **Unknown outcomes stay `unresolved`.** They are never recorded as `failed`, and every error after the intent is written names the txid. After a broadcast, `send` never returns an error; a wallet-save failure becomes a `warning` field.
- **"Not found" needs two sources.** The kit queries Blockbook explorers and PIVX Core RPC nodes (`getrawtransaction`) alternately. In practice both answering sources are PIVX Labs today, so they are not fully independent. "Found" requires the response to actually contain the transaction.
- **Bounded waits.** The spend lock waits at most 120 s, then errors without sending. The Sapling prover loads before the lock is taken. `balance` and `resync` take the lock because they write `wallet.json`.
- **Timestamps are read at each ledger write**, so an intent isn't stamped before slow guard lookups.
- **Known limitation:** a `broadcast` record is reused forever and is never re-checked for mempool eviction.
- **Fail closed on ledger reads.** Non-UTF-8 or non-JSON lines are skipped. Any other read error, a newer format version, or an unreadable `send_intent` blocks every payment, plain sends included.
- **`history` settles** unresolved records, and failed records up to a day old, only when no payment is in progress. It stops at the first unreachable lookup.
- **Smaller items:**
  - `history --csv` honors `--limit`.
  - `pivx_history` accepts numeric `since` and rejects `limit: 0`.
  - Card order ids are normalized for the guard.
  - The cards reason uses the first 12 characters of the order id.
- **CLI behaviour changes:**
  - Unquoted multi-word memos and stray extra arguments are now errors. They used to be silently truncated.
  - A memo starting with `--` is read as a flag.

## As built (PR 2)

- **Oracle endpoint.** The kit uses `/oracle/api/v1/price/usd`; the parser also accepts the `/currencies` array.
- **Price trust was redesigned after review.** A reviewer reproduced a first-run price about 100× too low being accepted. Now:
  - an hour-long **anchor** is the band reference, so the band can't be walked;
  - with no anchor, **two sources must agree within 10%**;
  - a source failing checks **falls through** to the next;
  - future-dated prices and cache entries are rejected;
  - the **display price is cached separately** and never used for spending;
  - failed display fetches are remembered for 60 s.
- **Recorded price.** Payments record a checked price only: the conversion price for a dollar amount, else a spending-grade price, else none. Never a display price.
- **Price fetches happen outside the spend lock.** HTTP connect and read are each capped at 5 s via the agent. DNS lookups aren't bounded by ureq.
- **`SendRequest.price`** carries the conversion price. This replaces the PR 1 note that `usd_price_e8` stays off `SendRequest`.
- **MCP `amount` / `amount_usd`** are strings; a number in either is an error. `"$5"` in `amount` is rejected.
- **Test builds sandbox the data directory** (`wallet::get_data_dir` under `cfg(test)`). During development, an MCP argument test reached the real data directory, which held no wallet. It created two files there, which were removed.

## As built (PR 3)

- **New modules:** `policy.rs` (model, evaluation, signed storage), `pending.rs` (queue), `gate.rs` (one testable decision function), `operator.rs` (terminal-gated commands behind a `Terminal` trait).
- **Approvals bind to the exact payment.** On replay, destination, amount, balance and trigger must match the held request.
- **Retries don't duplicate holds.** A retry for the same task or order reuses the open entry; plain sends each get their own.
- **No ledger events for policy and approvals.** `pending.json` keeps resolved entries as the audit trail.
- **A replay that fails** (for example, an expired card order) marks the entry `failed`. A replayed task bounty that paid but couldn't be recorded on the platform returns `paid_not_recorded` and the entry reads `approved`.
- **Changes after the PR 3 review:**
  - Approvals are consumed under the spend lock, so a second concurrent approve finds the entry taken. `pending.json` read-modify-writes take a separate `pending.lock`.
  - On replay, the caps are checked and the price recorded with a fresh spending-grade price (`price::price_for_payment`). The stored request-time price is shown in the prompt only.
  - Agent-supplied text is validated at the boundary: no control characters in `reason`, at most 280 characters. The prompt escapes every agent or platform field and prints kit-derived facts first. It also shows the memo and warns about duplicate held payments.
  - With a policy set, export needs a terminal; `pivx_export` refuses.
  - `policy set` on a tampered or corrupt file starts from scratch.
  - The MAC covers the stored policy value, so a policy written by a newer version (with extra fields) still verifies.
  - A retry with different details supersedes the held entry.
  - Validation rejects an approval threshold at or above the daily cap. A huge dollar limit saturates instead of blocking everything.
  - Price cache spend and anchor entries are MAC'd with a device subkey. With an anchor, the second source is cross-checked when it answers. Temp files are unique per write. The display path merges only its own fields.
- **Changes after the PR 3 verification pass:**
  - `pivx_task_submit` refuses attachments inside the data dir or at the machine-id paths, after resolving symlinks. On Linux, `wallet.json` plus `/etc/machine-id` is enough to decrypt the seed offline.
  - `pending.json` updates are compare-and-set (`resolve_from`). A deny only applies to a still-pending entry. An approval outcome is recorded only for an entry this process claimed (new `sending` status, `claimed_by` run token), so a crash leaves `sending` rather than a false `approved`.
  - Bidi and zero-width characters are rejected in reasons and escaped in prompts.
  - Policy fields this version doesn't know block spending instead of being ignored, so a downgrade fails closed.
  - The price cache uses a random per-process key if the device key is unavailable.
- **Positioning (operator decision):** limits are enforced against MCP-only agents. An agent with shell access can disable them by editing or deleting the kit's files. The README says this plainly; signing local state against shell-level tampering was considered and deferred.
- **Known limitations:**
  - a dollar amount held for approval keeps its request-time PIV amount (the caps are re-checked at today's price);
  - the policy and price MAC keys are derivable by anything that can run as the user;
  - `policy.json` deletion, policy rollback and ledger edits aren't detected;
  - DNS lookups aren't time-bounded.

## PR 1: Ledger and safe sends

### 1.1 `SendRequest` replaces the positional `core::send` signature

Today: `core::send(address, amount_sat, memo, from)`.

New, in `src/core.rs`:

```rust
pub struct SendRequest<'a> {
    pub address: &'a str,
    pub amount_sat: u64,
    pub memo: &'a str,
    pub from: Pool,              // enum { Private, Public }, no more stringly-typed "from"
    pub reason: Option<String>,  // free text, shown in history
    pub origin: Origin,          // what triggered this spend (see 1.3)
    pub usd_price_e8: Option<u64>, // set by PR 2; None in PR 1
}

pub fn send(req: SendRequest) -> Result
```

Call sites to update:
- `src/main.rs:114`: CLI `send`
- `src/mcp.rs:519`: `pivx_send`
- `src/task/commands.rs:558`: `task approve` auto-pay
- `src/cards/commands.rs:329`: `cards order pay`

`Pool` gets a `FromStr` that errors on anything other than `private` or `public`. That fixes the bug where `--from pubic` silently spent the private balance (`src/main.rs:102`). The CLI `send` default stays `private`, which is the current behavior. The flag just can't be mistyped silently anymore.

### 1.2 New module `src/ledger.rs`

An append-only `ledger.jsonl` in the data directory, `chmod 600` like `wallet.json`. Each line is one event:

```json
{"v":1,"event":"send_intent","id":"a1b2c3d4e5f60718","ts":1790880000,"wallet":"D...","to":"D...","amount_sat":50000000,"from":"public","memo":"","reason":"Bounty for task #12 to frosted-otter-417","origin":{"type":"task_approve","task_id":12,"worker":"frosted-otter-417"},"txid":"6f3d...","usd_price_e8":null}
{"v":1,"event":"send_broadcast","id":"a1b2c3d4e5f60718","ts":1790880002,"txid":"6f3d...","fee_sat":22800}
{"v":1,"event":"send_failed","id":"a1b2c3d4e5f60718","ts":1790880002,"error":"Broadcast failed — ..."}
```

PR 3 adds `policy_changed`, `pending_created` and `pending_resolved` events.

- **Writes:** one `write_all` of a single line to a file opened with `append(true)`. On POSIX, small appends to an `O_APPEND` file don't interleave, which covers the case of two MCP server processes sharing one data directory.
- **Reads:** `ledger::read_all()` parses line by line and skips malformed lines with a stderr warning. A torn last line from a crash must never block a send.
- **Reduction:** `ledger::sends(events) -> Vec<SendRecord>` folds the events by `id` into a status of `broadcast`, `failed` or `unresolved`. It's a pure function with unit tests.
- **Scoping:** every event carries `wallet` (the transparent address). Reads filter to the current wallet, the same pattern `task/state.rs` and `cards/state.rs` already use.

### 1.3 `Origin`

```rust
pub enum Origin {
    Send,                                          // plain pivx_send / CLI send
    TaskApprove { task_id: i64, worker: String },
    CardsPay { order_id: String },
}
```

Origin does two jobs. In PR 1 it lets a retry find an earlier payment, which is the double-payment fix. In PR 3 it's what a pending approval replays.

### 1.4 Write the intent before broadcasting

New flow inside `core::send`:

1. Sync, then build the transaction (unchanged).
2. Compute the txid locally from `txhex`: double-SHA256 of the raw bytes, byte-reversed, hex-encoded.
3. Append `send_intent` with that txid.
4. Broadcast.
5. On success, append `send_broadcast` with the txid and fee. On failure, append `send_failed` with the error.

If the process dies between steps 4 and 5, the intent already holds the txid, so the outcome can still be checked on chain later.

> **Verify first (step 0 of PR 1):** `pivx-wallet-kit` v0.2.4's `TransactionResult` and `TransparentTransactionResult` have no txid field. Their fields are `txhex`, `nullifiers`/`spent`, `amount` and `fee`. Confirm that double-SHA256 of the raw bytes matches the txid the network returns, for **both** shield (v3 Sapling) and transparent transactions, by comparing against the broadcast response on a small mainnet send. If it doesn't match for shield, the fallback is to write the intent without a txid and accept a slightly wider window where a crash leaves the outcome unknown. Both paths should also log a warning whenever the computed and returned txids differ.

### 1.5 Settling unresolved entries

`ledger::resolve_unresolved(net)` looks up the txid of each `unresolved` record through Blockbook `GET /api/v2/tx/<txid>` (new `PivxNetwork::tx_exists`, tried across `EXPLORERS`). Blockbook includes mempool transactions.

- If the txid is found, it appends `send_broadcast`.
- If the explorers say the txid doesn't exist, it appends `send_failed` with the error "not found on chain".
- If the explorers can't be reached, the record stays `unresolved`.

`history` and the double-payment guards (1.6) call this before trusting the ledger.

### 1.6 Double-payment guards

**`task approve`** (`src/task/commands.rs:470`), before auto-paying:

```
find the ledger send whose origin is TaskApprove{task_id, worker}
  broadcast   -> reuse its txid, skip core::send, go straight to POST /approve
  unresolved  -> refuse: "a payment for this approval may already be in flight (txid …); retry in a minute"
  failed/none -> pay as normal
```

Also include `txid` in the error message when `POST /approve` fails after a successful payment, so the agent and operator can see it, and point to `history`.

**`cards order pay`** (`src/cards/commands.rs:262`) gets the same guard, keyed on `CardsPay{order_id}`. The existing `status_num != 1` check doesn't fully cover this, because PIVCards may still report PENDING while the first payment sits unconfirmed in the mempool.

Both paths fill in a default `reason`: `"Bounty for task #<id> to <worker>"` and `"PIVCards order <id> (<slug> <amount>)"`.

### 1.7 `history` command and `pivx_history` tool

```
pivx-agent-kit history [--limit N] [--since <unix-ts|YYYY-MM-DD>] [--csv]
```

The output is newest first:

```json
{ "count": 2,
  "sends": [ { "id": "...", "ts": 1790880000, "time": "2026-10-01T09:20:00Z",
```

## PR 2: Dollar amounts

### 2.1 New module `src/price.rs`

- **Primary source:** PIVX Labs Oracle `GET https://pivxla.bz/oracle/api/v1/currencies`. It returns an array of `{"currency":"usd","value":0.06888275,"last_updated":1790879206}`, where `value` is the USD price of 1 PIV. Checked live on 2026-10-01.
- **Fallback:** CoinGecko `GET https://api.coingecko.com/api/v3/simple/price?ids=pivx&vs_currencies=usd`.
- **Override:** the `PIVX_PRICE_API` environment variable, matching the existing `PIVX_TASKS_API` and `PIVCARDS_API` convention.
- **Cache:** `price_cache.json` in the data directory, `{ "usd_e8": u64, "fetched_at": u64, "source_updated_at": u64, "source": "oracle" }`.
- **Freshness:**
  - Spending conversions need a price fetched within the last 60 seconds, so they refetch if the cache is older.
  - Display allows a price up to 10 minutes old.
  - Any price whose `last_updated` is more than 30 minutes old is rejected for spending.
- **Sanity check:** if a fresh price differs from the cached one by more than 25% within an hour, refuse USD spending with the error "price moved >25% in <1h, use a PIV amount or retry". The worry is a bad price feed making a "$5" send cost 50× the PIV. Display is unaffected.
- **Timeouts:** 5 seconds per request, so `balance` never stalls on a slow price feed.

### 2.2 Integer math

The price is stored as `usd_e8`, the USD per PIV × 10⁸, rounded once when the API's float is read. Everything after that uses integers:

```
usd_e8_amount = parse_piv_to_sat(usd_string)              // reuse the existing exact 8-dp decimal parser
sat           = (usd_e8_amount as u128 * 100_000_000 + price_e8 / 2) / price_e8   // round half up
usd_e8_of_sat = (sat as u128 * price_e8 + 50_000_000) / 100_000_000
```

Reject a price of zero, and reject any result that overflows `u64` or rounds to 0 sat.

### 2.3 Surfaces

- **CLI `send`:** the amount accepts `$5`, `5usd` or `5 USD` as well as plain PIV (`5`). A `--usd` flag is equivalent. A USD amount gets converted once, up front, and the PIV amount is shown in the output.
- **MCP `pivx_send`:** new optional `amount_usd` (decimal string). Exactly one of `amount` or `amount_usd` is required; passing both is an error.
- **Send output** gets these extra fields: `"amount_usd": "5.00", "price_usd": "0.06888275", "price_source": "oracle"`. They're present whenever a price is available, including PIV-denominated sends, because the ledger records the price at send time either way.
- **`balance`, `resync`:** add `private_balance_usd`, `public_balance_usd`, `total_balance_usd` and `price_usd` when a price is available. Leave the fields out (don't null them) when it isn't, and never fail the command because of the price feed.
- **`history`:** each send shows `amount_usd` computed with the price recorded at send time (`usd_price_e8` in the intent event).
- **`cards order pay`:** add `amount_usd` to the output when a price is available. It doesn't change any behavior.

### 2.4 Tests (PR 2)

- Conversion table: `$5` at 0.06888275 (`price_e8` = 6888275) → 7258711361 sat (≈72.587 PIV); rounding at .5; tiny amounts that round to 0 are rejected; large amounts don't overflow `u128`.
- Amount parsing: `$5`, `5usd`, `5 USD`, `5.123456789usd` (more than 8 decimal places is rejected), `$`, `usd`.
- Freshness and sanity-band decisions as pure functions over `(cache, fresh, now)`.
- Oracle response parsing: picks the `usd` entry, errors when it's missing, ignores other currencies.

## PR 3: Spending policy and human sign-off

### 3.1 Policy model (`src/policy.rs`)

```rust
pub struct Policy {
    pub max_per_tx: Option<Limit>,       // hard block above this
    pub max_daily: Option<Limit>,        // hard block if rolling-24h spend + this spend exceeds it
    pub approve_above: Option<Limit>,    // anything above → pending, needs operator
    pub allowlist: Vec<String>,          // if non-empty, any other destination → pending
    pub updated_at: u64,
}

pub enum Limit { Piv(u64 /* sat */), Usd(u64 /* usd_e8 */) }
```

**Rules:**
- "Max" means never. "Approve above" means ask first. An operator approval clears `approve_above` and the allowlist, but never `max_per_tx` or `max_daily`. To go over a hard limit, the operator raises it.
- `policy set` rejects a configuration where `approve_above >= max_per_tx`.
- **The daily total** is the rolling 24 hours of `broadcast` and `unresolved` sends from the ledger, fees included, plus the new amount. `unresolved` counts toward the total, so a crash can't be used to get around the cap. The fee of the spend being checked isn't known before the transaction is built, so it isn't counted. Fees are a few thousandths of a PIV, and the README should say this explicitly.
- **USD limits** are converted with the same fresh price as 2.1. If no price is available, the spend is blocked: "can't evaluate USD limit: price unavailable; retry or ask your operator to set PIV limits."

The evaluation is a pure function:

```rust
pub fn evaluate(policy: &Policy, req: &SpendCheck, spent_24h_sat: u64, price_e8: Option<u64>, approved: bool) -> Decision
pub enum Decision { Allow, NeedsApproval(Vec<String>), Deny(String) }
```

Reasons are human-readable, for example "amount $12.00 exceeds approval threshold $10.00".

### 3.2 Storage and tamper detection

- The policy is stored in `policy.json` in the data directory as `{ "policy": {...}, "mac": "<hex>" }`.
- `mac` is an HMAC-SHA256 over the canonical JSON of `policy`. Its key is derived the same way as `wallet::device_key()`, with a different domain tag (`"pivx-agent-kit-policy-mac"`). That needs one new dependency, the `hmac` crate from RustCrypto, which fits next to the existing `sha2`.
- A file whose MAC doesn't match means every spend is blocked with "policy file was modified outside `pivx-agent-kit policy`; run `policy show` to inspect and `policy set` to re-sign." This catches an agent editing the JSON by hand.
- With no file, there is no policy and behavior matches v0.6.1.

### 3.3 Operator-only commands (TTY-gated)

```
pivx-agent-kit policy show                      # works anywhere, prints JSON
pivx-agent-kit policy set [--max-tx L] [--daily L] [--approve-above L] [--allow <addr>]... [--clear-allowlist]
pivx-agent-kit policy clear
pivx-agent-kit pending list                     # works anywhere
pivx-agent-kit pending approve <id>
pivx-agent-kit pending deny <id>
```

`L` takes the same amount syntax as send: `25` (PIV) or `$25`.

`policy set`, `policy clear`, `pending approve` and `pending deny` require stdin to be a terminal (`std::io::IsTerminal`, stable since Rust 1.70, which is already the kit's minimum version). They print a summary and ask for `y` to confirm. Agent shell tools such as Claude Code's Bash run without a TTY, so an agent calling these commands gets an error: "this command must be run by a human in an interactive terminal."

None of these get MCP tools.

**Honest caveat, which goes in the README word for word:** this is a spending limit, not a security boundary. An agent with unrestricted shell access could still find ways around it, for example by deleting the data directory or running a `script` pseudo-terminal. It stops runaway loops, prompt-injected "send everything" instructions and fat-fingered amounts. It doesn't stop an adversarial agent that has full control of the machine.

### 3.4 Pending approvals (`src/pending.rs`)

- Pending approvals are stored in `pending.json` in the data directory. Each entry has an `id`, `created_at` and `expires_at` (24 hours later), the `Origin`, the full `SendRequest` (sat amount fixed at request time), the reasons it needs approval, and the USD value at request time.
- `core::send` runs `policy::evaluate` before building the transaction.
  - On `NeedsApproval`, it writes a pending entry, appends a `pending_created` event to the ledger, and returns **`Ok`**, not `Err`, so the agent passes the message on instead of retrying:
    ```json
    { "status": "pending_approval", "pending_id": "p_7f3a…", "amount": 145.2, "amount_usd": "10.00",
      "reasons": ["amount $10.00 exceeds approval threshold $5.00"],
      "next_step": "Tell your operator to run: pivx-agent-kit pending approve p_7f3a…" }
    ```
    The CLI exits with code 2 for `pending_approval`, so shell scripts can't mistake it for a completed send.
  - On `Deny`, it returns `Err("blocked by spending policy: …")`.
- `pending approve <id>` replays the stored origin with `approved = true`:
  - `Send`: calls `core::send` with the stored request.
  - `TaskApprove`: reruns `task approve` for that task and worker. The PR 1 guard still applies, and the platform's `POST /approve` happens here.
  - `CardsPay`: reruns `cards order pay`, which re-checks that the order is still PENDING. PIVCards invoices expire, so an approval that comes too late fails cleanly with "order expired, create a new one."
- An expired entry can't be approved.
- `task approve` and `cards order pay` pass the `pending_approval` result straight through, and don't call the platform until the payment actually goes out.

### 3.5 Read-only MCP tools

- `pivx_policy`: returns the current policy with limits in both PIV and USD, the rolling 24-hour spend, and how much is left today. This lets the agent plan around its limits instead of finding them by hitting them.
- `pivx_pending_list`: lists the agent's own pending requests and their status.
- Update the descriptions of `pivx_send`, `pivx_task_approve` and `pivx_cards_order_pay` to say that the result may be `status: "pending_approval"`, that the agent should tell the user, and that it shouldn't retry.

### 3.6 Tests (PR 3)

- `evaluate` table tests:
  - each limit on its own
  - PIV and USD limits combined
  - USD limit with no price → Deny
  - `approved = true` clears the approval threshold and allowlist but not the hard caps
  - allowlist hit and miss
  - daily-total boundary, with `unresolved` sends counted
- MAC: round-trip, a one-byte edit gives a mismatch, a missing file means no policy.
- `policy set` validation: `approve_above >= max_per_tx` is rejected.
- The TTY gate sits behind a small trait (`trait Terminal { fn is_interactive() -> bool; fn confirm(prompt) -> bool }`) so tests can inject it.
- Pending: create, list, approve replays the right origin, expired approvals are rejected, deny marks the entry as resolved.

## Manual mainnet smoke test (before tagging)

Use a fresh wallet funded with about 5 PIV.

1. `send` 0.01 PIV public→public and private→public with `--reason`. Check that the computed txid equals the broadcast txid for both, and that `history` shows both as `broadcast`.
2. Kill the process (`kill -9`) right after the broadcast log line. Check that `history` shows the send as `unresolved` and that it becomes `broadcast` on the next call.
3. `send '$0.10'`. Check the PIV amount against the oracle by hand.
4. `policy set --max-tx '$1' --daily '$2' --approve-above '$0.25'` in a terminal. Then:
   - Running the same command through a non-TTY pipe (`echo | pivx-agent-kit policy set …`) must be refused.
   - A `$0.20` send goes through.
   - A `$0.50` send returns pending with exit code 2. `pending approve` sends it.
   - A `$1.50` send is denied.
   - Repeated sends hit the daily cap.
5. Edit `policy.json` by hand and check that every spend is blocked with the tamper message.
6. Over MCP from Claude Code, ask the agent to send `$0.50`. Check that it relays the pending message and doesn't retry.
7. `task approve` on a staging task (`PIVX_TASKS_API`) with the platform call made to fail. Check that the retry reuses the txid and doesn't pay a second time.

## Decisions already made (call out in review if you disagree)

1. Operator approval can't override the hard caps (`max_per_tx`, `max_daily`).
2. No policy file means no limits, so existing installs behave exactly as before. `init` prints a one-line hint suggesting `policy set`.
3. Sends that are `unresolved` count toward the daily cap.
4. A pending send keeps the PIV amount fixed when it's created. The approval prompt shows its USD value at request time and at approval time.
5. Pending approvals expire after 24 hours.
6. The CLI exits with code 2 for `pending_approval`.
7. The PIVX Labs Oracle is the primary price source and CoinGecko is the fallback.
